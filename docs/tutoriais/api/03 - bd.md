# Banco de dados e migrations

Nesta etapa, configuramos a conexão com PostgreSQL, definimos o model da tabela de canais e preparamos o Alembic para versionar as alterações na estrutura do banco.

Migrations alteram tabelas, colunas, índices e outras estruturas do banco. Mudanças nas rotas e nas regras da aplicação continuam sendo feitas no código Python.

## Dependências

Execute dentro de `integracao-hellow`, onde está o `pyproject.toml`:

```powershell
uv add sqlalchemy "psycopg[binary]" alembic
```

- `sqlalchemy`: representa tabelas como classes Python e fornece sessões para consultar e persistir dados.
- `psycopg[binary]`: driver de comunicação com PostgreSQL; a distribuição binária facilita a instalação sem compilação local.
- `alembic`: gera e aplica migrations, mantendo um histórico versionado das alterações do banco.

## Conexão: provider/database.py

```python
import os

from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, sessionmaker

DATABASE_URL = os.environ["DATABASE_URL"]

engine = create_engine(DATABASE_URL, pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine)


class Base(DeclarativeBase):
    pass


def get_db():
    with SessionLocal() as session:
        yield session
```

`DATABASE_URL` vem do ambiente para separar a configuração de conexão do código. A variável precisa existir antes de importar esse módulo. Essa configuração não carrega arquivos `.env` automaticamente.

O `engine` gerencia as conexões com o PostgreSQL. Criá-lo não cria tabelas nem verifica imediatamente a disponibilidade do servidor: a conexão é aberta quando necessária. `pool_pre_ping=True` testa uma conexão retirada do pool antes de reutilizá-la, ajudando a detectar conexões encerradas pelo servidor.

`SessionLocal` é uma fábrica de sessões. A sessão organiza consultas e alterações. O `get_db()` disponibiliza uma sessão e garante seu fechamento ao terminar; ele não confirma escritas automaticamente. Para persistir alterações, o código da aplicação precisará chamar `commit()`.

`Base` é a classe comum dos models SQLAlchemy. Seu `metadata` reúne as definições das tabelas e será usado pelo Alembic.

## Model: models/canais_db.py

O arquivo `models/canais.py` contém os schemas Pydantic de entrada e saída da API. Já `models/canais_db.py` representa a tabela no PostgreSQL.

- `Canal(Base)`: registra a definição da tabela no metadata da Base.
- `__tablename__ = "canais"`: define o nome da tabela.
- `Mapped[...]`: declara o tipo Python do atributo.
- `mapped_column(...)`: configura a coluna no banco.
- `primary_key=True`: identifica a chave primária.
- `String(100)` e `String(20)`: definem limites de tamanho para os textos.
- `Uuid`: representa o identificador UUID.
- `DateTime(timezone=True)`: representa uma data com suporte a fuso horário no PostgreSQL.

Os atributos `Mapped[str]`, sem tipo opcional, são obrigatórios por padrão. Declarar `status` e `ambiente` como texto não cria automaticamente no banco as restrições dos enums Pydantic.

Como a conexão está em `provider/database.py`, o import correto no model é:

```python
from provider.database import Base
```

Para gerar a data de criação a cada inserção, use:

```python
criado_em: Mapped[datetime] = mapped_column(
    DateTime(timezone=True),
    default=lambda: datetime.now(timezone.utc),
)
```

`default=datetime.now(timezone.utc)` calcula a data uma única vez, ao importar o módulo. A função `lambda` calcula uma nova data a cada inserção pelo SQLAlchemy. Pelo mesmo motivo, o UUID usa `default=uuid4`, sem chamar a função imediatamente.

Esses defaults são executados pelo SQLAlchemy; não são defaults definidos no servidor PostgreSQL.

## Inicialização do Alembic

```powershell
uv run alembic init migrations
```

Esse comando prepara os arquivos do Alembic, mas não cria as tabelas da aplicação:

```text
integracao-hellow/
├── alembic.ini
├── migrations/
│   ├── env.py
│   ├── script.py.mako
│   └── versions/
├── models/
│   └── canais_db.py
└── provider/
    └── database.py
```

- `alembic.ini`: configura a localização dos scripts e os logs.
- `env.py`: conecta o Alembic ao banco e aos models.
- `script.py.mako`: template usado para gerar os arquivos de revisão.
- `versions/`: armazena o histórico das migrations.

No `alembic.ini`, `script_location = %(here)s/migrations` localiza os scripts em relação ao arquivo de configuração. `prepend_sys_path = .` permite importar os módulos da pasta atual. Por isso, executamos os comandos dentro de `integracao-hellow`.

## Configuração de migrations/env.py

O arquivo deve reutilizar o engine da aplicação e registrar os models que o Alembic precisa conhecer:

```python
from logging.config import fileConfig

from alembic import context

from provider.database import Base, engine
from models.canais_db import Canal

config = context.config

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=engine.url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )

    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    with engine.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
        )

        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

### Imports e metadata

Importar `Canal` executa a declaração da classe e registra sua tabela em `Base.metadata`. Mesmo sem usar a classe diretamente nesse arquivo, a importação é necessária. Outros models também precisarão ser importados, diretamente ou por um módulo que reúna todos eles.

`target_metadata = Base.metadata` informa a estrutura desejada. Com `--autogenerate`, o Alembic compara essa estrutura com o banco conectado para propor uma migration.

Reutilizar o `engine` evita manter configurações de conexão diferentes para aplicação e migrations. Nesse fluxo, o valor de exemplo `sqlalchemy.url` no `alembic.ini` não é utilizado e pode ser removido. Os imports gerados de `engine_from_config` e `pool` também deixam de ser necessários.

`fileConfig` configura os logs conforme o `alembic.ini`, permitindo acompanhar as revisões executadas.

### Modo online

`engine.connect()` abre a conexão real com o banco. `context.configure` recebe essa conexão e os metadados dos models.

`context.begin_transaction()` delimita a transação; no PostgreSQL, as operações usuais de criação e alteração de tabelas participam dela. `context.run_migrations()` executa as operações das revisões selecionadas pelo comando.

Esse modo é usado normalmente para gerar migrations com `--autogenerate` e aplicá-las com `upgrade head`.

### Modo offline

O modo offline gera SQL sem conectar ao servidor, por exemplo:

```powershell
uv run alembic upgrade head --sql
```

- `url=engine.url`: informa o dialeto do banco. A variável `DATABASE_URL` ainda precisa existir, pois o módulo da conexão é importado.
- `literal_binds=True`: solicita que valores compatíveis sejam escritos diretamente no SQL gerado.
- `dialect_opts={"paramstyle": "named"}`: configura o formato de parâmetros usado pelo dialeto nesse contexto.

Esse modo permite revisar ou entregar um script SQL para execução posterior. Ele não substitui a conexão necessária para comparar o banco com os models usando `--autogenerate`.

### Seleção do modo

O bloco final com `context.is_offline_mode()` chama a função correspondente. Apenas definir as funções não executa as migrations; esse bloco precisa estar presente.

## Configurar o endereço do banco

No terminal PowerShell em que executará o Alembic:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://usuario:senha@localhost:5432/integracao"
```

Substitua os valores pelos dados do seu ambiente. O PostgreSQL precisa estar acessível e o banco `integracao` já deve existir. As migrations criam tabelas dentro do banco; não criam o banco PostgreSQL em si.

Esse endereço considera o Alembic executado no Windows e o PostgreSQL disponível na porta local `5432`. Dentro de um container, `localhost` aponta para o próprio container; o endereço deve ser ajustado conforme onde o PostgreSQL está rodando.

## Gerar, revisar e aplicar a primeira migration

```powershell
uv run alembic revision --autogenerate -m "criar tabela canais"
```

O comando gera um arquivo em `migrations/versions/`, sem aplicar a alteração. Revise se o `upgrade()` contém `op.create_table("canais", ...)` e se o `downgrade()` contém a operação inversa, `op.drop_table("canais")`.

A geração automática precisa de revisão: renomear uma coluna pode aparecer como remover uma coluna e adicionar outra, exigindo ajuste manual para preservar dados.

Depois da revisão:

```powershell
uv run alembic upgrade head
uv run alembic current
```

`upgrade head` aplica as revisões pendentes até a mais recente. `current` mostra a revisão aplicada. O Alembic registra o estado na tabela `alembic_version`.

Cada arquivo possui `revision`, seu identificador, e `down_revision`, a revisão anterior. Essa ligação define a ordem do histórico. `upgrade()` descreve como avançar; `downgrade()` descreve como voltar. Uma reversão que remove tabelas ou colunas pode apagar os dados correspondentes.

## Próximas alterações

O fluxo de trabalho será:

1. Alterar o model SQLAlchemy.
2. Gerar uma nova revisão com `uv run alembic revision --autogenerate -m "descricao da alteracao"`.
3. Revisar as operações e considerar os dados existentes.
4. Aplicar com `uv run alembic upgrade head`.

Por exemplo, adicionar uma coluna obrigatória a uma tabela preenchida pode exigir preencher os registros existentes antes de impor a obrigatoriedade.

Versione no Git os models, o `alembic.ini` e a pasta `migrations/`. Depois que uma migration for aplicada e compartilhada, registre novas mudanças em outra revisão para preservar o histórico.

Nesse fluxo, não usamos `Base.metadata.create_all()` para criar tabelas. A criação e a evolução da estrutura ficam registradas nas migrations.

Este documento explica a configuração e os ajustes; não modifica esses arquivos Python. As rotas também continuam precisando ser adaptadas para persistir os canais no PostgreSQL.
